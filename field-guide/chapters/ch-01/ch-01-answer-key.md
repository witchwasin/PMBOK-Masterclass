# Answer Key — Chapter 01 (Pre-sales)

Instructor-facing only. ใช้เกณฑ์แนวทาง (rubric) ต่อไปนี้ประเมิน — ไม่ใช่คำตอบเดียวที่ถูก

## Assessment Composition

| Section | Share | Type |
|---|---:|---|
| Decision Case | ~55% | Application and judgement |
| Trade-off Case | ~15% | Application |
| Artifact Review | ~15% | Artifact review |
| Executive Communication | ~10% | Application |

## Model Answers

### 1. [Decision Case] ลูกค้าขอเพิ่ม Mobile App ทั้งที่ RFP ระบุแค่ Website

**แนวตอบ:** ไม่ตอบรับทันที — ขอ evidence ก่อน:
- ขอ clarify: Mobile App จำเป็นกับ business objective ใด (ตรงกับ 35% direct booking หรือไม่)
- ขอ scope detail: ฟีเจอร์ใน App คืออะไร platform ไหน iOS/Android ทั้งคู่?
- ทำ Impact Analysis: effort, timeline, PMS/payment dependency, QA scope

**Options (อย่างน้อย 3):**
- A. รับเข้า Proposal โดยเพิ่มราคา/เวลา (ต้องมีตัวเลข impact)
- B. เสนอ App เป็น Phase 2 (หลัง launch website ก่อน) — เหมาะกับ high-season deadline
- C. เสนอเป็น Option ใน Proposal (Base = website, Option = app) ให้ลูกค้าเลือก

**เกณฑ์ผ่าน:** มี missing information ที่ระบุได้, มี options ≥ 3, ไม่มีคำว่า "รับเลย"

### 2. [Decision Case] Sales เสนอราคา 9 ล้าน Fixed แต่ ROM คือ 9.5–12 ล้าน

**แนวตอบ:** แนะนำ CEO ว่าอย่าเสนอราคาต่ำกว่า ROM โดยไม่มีเหตุผล:
- อธิบายว่า ROM มาจาก functional leads มี basis + assumptions
- ถ้าราคา 9 ล้าน ต้องชี้ชัดว่า scope ไหนถูกตัด หรือ margin ไหนถูกยอมแลก
- ทางเลือก: ลด scope ให้ match ราคา, ขอเพิ่ม budget, เสนอ hybrid, หรือ No-Bid
- เตือน risk: ราคาต่ำกว่า ROM = delivery risk สูง → ส่งมอบไม่ได้ → เสียชื่อเสียง + penalty

**เกณฑ์ผ่าน:** ตอบโดยอ้าง ROM basis ไม่ใช่ความเห็น, มีทางเลือกที่ทำให้ราคากับ scope สอดคล้อง

### 3. [Trade-off Case] Fixed Price vs T&M สำหรับ PMS integration ที่ API ยังไม่ชัด

**แนวตอบ:**
- Fixed Price: vendor รับ cost risk → เหมาะเมื่อ scope ชัด แต่ PMS API ไม่ชัด → vendor จะใส่ buffer สูง หรือเจอ dispute ภายหลัง
- T&M: ยืดหยุ่นกับงานที่ต้องเรียนรู้ แต่ต้องมี rate, cap, approval cadence, acceptance, change control ไม่เช่นนั้นบานปลาย
- Hybrid (แนะนำในกรณีนี้): fixed สำหรับ core dev, T&M แบบมี cap สำหรับ PMS adapter

**เกณฑ์ผ่าน:** อธิบาย risk allocation ครบสองฝั่ง และเสนอทางเลือกที่สอดคล้องกับความไม่ชัดของ scope

### 4. [Artifact Review] Proposal ที่ไม่มี Out of Scope และ Assumptions

**แนวตอบ:** เมื่อเซ็นไปแล้ว:
- ทุกอย่างที่ลูกค้าขอเพิ่ม = "ใน scope" โดยปริยาย → scope dispute ตอนส่งมอบ
- Assumption ไม่ถูกบันทึก → ถ้าผิด (เช่น PMS API พร้อม) กลายเป็นต้นทุนที่ vendor ต้องแบกเอง
- ไม่มี Client Responsibilities → ลูกค้าไม่ต้องส่งข้อมูล/อนุมัติ → timeline ล่าช้าแต่ vendor โดนโทษ
- แก้โดย: เพิ่มหัวข้อ Out of Scope + Assumptions + Dependencies + Client Responsibilities ก่อนส่ง

**เกณฑ์ผ่าน:** ระบุผลกระทบ ≥ 3 ด้าน และวิธีการแก้

### 5. [Executive Communication] ทำไมต้องเพิ่ม Paid Discovery Phase

**แนวตอบ (1 ย่อหน้า):** เนื่องจากความไม่ชัดเจนของ PMS API ทั้ง 12 โรงแรมทำให้ ROM มี confidence ต่ำ การทำ Paid Discovery (เช่น 2–3 สัปดาห์, ราคา X แสนบาท) จะช่วยยืนยัน feasibility และล็อก scope ก่อนผูกพันสัญญาเต็ม ลดความเสี่ยงที่ margin จะถูกกลืนโดยงานที่คาดไม่ถึง และเพิ่มความแม่นยำของ Proposal — ต้นทุนเล็กน้อยเมื่อเทียบกับความเสี่ยงของสัญญาเต็ม

**เกณฑ์ผ่าน:** กระชับ, มีตัวเลข, โยงกับ value/risk ของบริษัท

### 6. [Cross-Knowledge Analysis] launch ก่อน High Season แต่ PMS integration ใช้ 6 เดือน

**แนวตอบ:**
- Scope: แยก integration ออกเป็น wave — 3 โรงแรมแรกก่อน (สอดคล้องกับ Soft Launch ใน Scenario Master) หรือขอ PMS vendor ทำ adapter เร็วขึ้น
- Timeline: ยอมให้ launch เป็นแบบ phased (ไม่ใช่ big-bang) หรือเลื่อน campaign
- Price: เพิ่ม T&M สำหรับ integration หรือขอให้ SHG รับส่วนที่เกิน
- Decision owner: CEO/Commercial (BTS) + ลูกค้า (Sponsor) — ต้องมี decision record

**เกณฑ์ผ่าน:** เห็นผลข้าม scope/timeline/price และระบุ decision owner

### 7. [Recall] ROM vs ราคาผูกพัน

**แนวตอบ:** ROM คือช่วงประมาณการ (มี assumptions + confidence) ใช้ตัดสินใจเชิงกลยุทธ์ ไม่ใช่ commitment ราคาผูกพันคือตัวเลขที่เข้า Proposal/SOW แล้ว ซึ่งต้องมี basis รองรับ

**เกณฑ์ผ่าน:** แยกช่วง/สมมติฐาน ออกจากราคาสัญญา

## Rubric สรุป

| ระดับ | เกณฑ์ |
|---|---|
| Professional | มี evidence, options, trade-off, owner, authority ครบ และเชื่อมกับ Scenario Master |
| Usable | ตอบถูกประเด็นหลัก มี options แต่ยังไม่ระบุ owner/authority |
| Incomplete | ตอบสั้น/เป็นความเห็น ไม่มี evidence หรือใช้คำว่า "รับเลย/ทำได้" โดยไม่วิเคราะห์ |
